# ADR-012 场景包加载与选择（G5 设计）

日期：2026-09-22 ｜ 状态：**已落地（按推荐默认 sign-off）** ｜ 依赖：ADR-007（场景包软分离）、MCP-CONTRACT

## 背景与缺口

ADR-007 规定了场景包目录结构（persona / agents / safety / mobility / physical_caps），但**只定义了"放什么"，没定义"谁加载、怎么选、怎么用"**。当前代码库的真实状态：

- `brain/core/capability.py` 只 `load_capability(<model>.yaml)`（能力注册表），**没有任何代码加载 `brain/packs/`**；
- `SuiyueBrain` 只做 `dispatch_emote`（emotion→动作，查能力注册表），**不装配 LLM system prompt、不选 Agent、不加载安全策略**；
- `brain/packs/` 下三个包（elder_cn_v1 / kids_v1 / pepper_cn_v1）目前是**文档/资产骨架**，运行时完全没被引用；
- LLM 的 system prompt 实际位于 fork 的 `xiaozhi-esp32-server`（本仓 overlay），场景包内容**到不了 LLM**。

这导致：即便 `pepper_cn_v1` 写好了，Pepper 会话也不会用上它的 persona / safety / companion Agent——大脑侧缺一套"加载 + 选择 + 暴露"机制。这就是 G5。

## 决策

### 1. 包清单（manifest）约定

每个 pack 的**根内容文件**携带 manifest 元信息（不新增单独文件，避免目录膨胀）：

- 完整包：根 `persona.yaml` 顶层带 `scene_pack` / `version` / `device_model` / `inherits?` / `status`；
- PoC 包（kids_v1）：根 `scene.yaml` 带上述字段（§5 允许豁免）。

字段语义：

| 字段 | 必填 | 说明 |
|---|---|---|
| `scene_pack` | 是 | 包 id，等于目录名 |
| `version` | 是 | 语义化版本；同 `device_model` 多包时取最高 |
| `device_model` | 是* | 关联能力注册表 model（如 `pepper_v1`）；PoC 包可缺 |
| `inherits` | 否 | 父包 id，内容继承（§3） |
| `status` | 否 | `skeleton` / `poc_slot_only` / `active` |

> *pepper_cn_v1 已声明 `device_model: pepper_v1` + `inherits: elder_cn_v1`，与本约定一致，无需改。

### 2. 加载器 `brain/packs/loader.py`

```
discover_packs(packs_dir) -> list[str]            # 列子目录 = 包 id
load_pack_raw(pack_id) -> dict                    # 读目录内全部 YAML → 结构化 dict
resolve_inheritance(pack_id) -> ResolvedPack      # 展开 inherits（§3）
validate_pack(resolved) -> list[warn]             # 必填校验 + 引用完整性
```

`ResolvedPack` 结构（合并后）：

```
{
  "manifest": {...},
  "persona": {...},          # 来自 persona.yaml（或 scene.yaml）
  "safety": {...},           # 来自 safety.yaml
  "agents": {name: {...}},   # agents/*.yaml 并集（继承时父+子文件并集）
  "mobility": {...} | None,  # 可选
  "physical_caps": {...} | None,
}
```

### 3. 继承合并算法（pepper_cn_v1 inherits elder_cn_v1）

目录级并集 + 文件级深合并：

- **agents/ 目录**：父包与子包的 agent 文件**取并集**（pepper 的 `companion` + elder 的 `health` 同时生效）；同名文件子包覆盖父包；
- **同一文件内的 dict**：递归深合并，**子包同键覆盖父包**（pepper 的 `persona.voice` 覆盖 elder 的同键；pepper 新增 `safety.physical` 作为新键并入）；
- **同一文件内的 list**（如 `safety.hard_rules`、`agent.tools`）：**v1 默认子包整体替换父包同键 list**（可预测、无隐式叠加）；需要叠加的语义（如"在父规则后追加"）留作 §6 开放决策；
- `inherits` 链深度不限，递归自底向上合并（子胜父）。

> 实证：pepper_cn_v1 的 `safety` 只重写了域规则 + 新增 `physical` 子键，未重列 `hard_rules`；dict 深合并即可保留 elder 的 `hard_rules` 并并入 `physical`。✅ 算法不破坏现有包。

### 4. 选择机制 `SceneManager`

```
# 挂在 SuiyueBrain 上
brain.scene_for(device_id) -> ResolvedPack | None
```

解析优先级（从高到低）：

1. **显式 scene**（会话参数，如 xiaozhi server 在 `get_scene` 调用里传 `scene=pepper_cn_v1`）→ 直接装载；
2. **device_model 匹配**：`model = brain._devices[did][0]`（即能力注册表的 model）→ 选 `device_model == model` 的包；同 model 多包取 `version` 最高；
3. **default 回退**：config 里的 `default_scene`（建议 `elder_cn_v1`）→ 用于未匹配模型或 PoC 演示。

结果按 `device_id` 缓存（会话级，模型不变则不重算）。

### 5. 运行时接线 + 暴露给 fork 的 xiaozhi server

大脑把"已选场景"暴露给 LLM 所在的 xiaozhi server，需新增一个 MCP 工具（改契约，走本 ADR）：

**`self.suiyue.get_scene`**（MCP-CONTRACT §8 新增）

```json
{ "tool": "self.suiyue.get_scene",
  "parameters": { "device_id": "pepper-01", "scene?": "pepper_cn_v1" } }
// 返回：组装好的 { persona, safety(hard_rules+disclaimer+emergency),
//        agents:[{name, system_prompt, tools, trigger_examples}], emotion_calibration }
```

消费约定（fork 纪律，server 侧薄改动）：

- xiaozhi server 在**会话开始**调用 `self.suiyue.get_scene(device_id)`；
- 用返回内容**组装 LLM system prompt**（persona + 各 agent.system_prompt + safety.hard_rules/disclaimer 作为护栏）、声明可用 `tools`（agent.tools 里的 `self.pepper.*` / `profile.*` / `knowledge.*`）；
- **场景内容只存 brain/packs**，server 不硬编码任何 persona/safety 文案 → 满足"端侧 OS 透明 / 场景热切换"原则。

> 不新增 HTTP 服务：server 本就是大脑 MCP 的 client，`get_scene` 复用现有 MCP 通道，零新传输。
