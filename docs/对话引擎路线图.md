### 🔴 1.2 G4 · 单server 绑多本体的device_id 歧义（**新发现，建议优先**）

- **问题**：overlay X1 用的是**静态配置** `suiyue.device_id: pepper-01`。
  但 `xiaozhi-server` 是**单进程多设备**——Otto / Reachy / Pepper / 大亮
  都连同一个 server。静态配置回答的是"**这个 server 是谁**"，
  而实际需要的是"**当前这条 WS 连接是谁**"。
- **后果**：四本体共机时，Pepper 的对话会拿到 Otto 的场景包（或反之），
  且 `get_scene(device_id)` 取错包 → 注入错误 persona。
- **✅ 决策（用户 2026-10-06）：方案 a —— 每本体一台 server**。
  → X1 的静态 `device_id` **语义正确，无需第 4 处 overlay 改动**，薄改动纪律保持不变。
  → **资源可行性已核算**：ADR-011 server-only 单实例仅需 **2–4GB RAM**，
  4 个 server 进程 ≈ 8–16GB 内存，与 4090 显存（LLM 独占约 9.5–11GB）
  是**不同资源池，不冲突**。
  → **落地形态**：4090 上用 docker compose 起 4 个 service，
  各自挂自己的 `config.yaml`（`suiyue.device_id` 不同），**共用同一个大脑 MCP server**。
- **遗留待办（⚠️ 需在 B 段处理）**：
  - 4 个 server 会各自拉起一个 stdio 大脑 MCP 子进程（stdio 拉起是 per-process），
    需确认这对大脑侧负载可接受。**建议**：每个 server 启动时都调 `warmup()` 预热
    （否则每个 server 的首个会话都要等~13s）。
  - 场景包缓存是 per-进程，4 个进程各持一份（体积可忽略，但要知道不共享）。
- **验收**：4 个 server 的 `get_scene` 分别返回各自正确的 `scene_pack`，互不串包。

### ✅ 1.3 意图与情绪的耦合 —— **已完成（2026-10-06）**

- **问题**：`get_emotion` 靠**扫描 LLM 回复里的第一个 emoji** 判定情绪。
  → **LLM 不吐 emoji → 永远 `neutral` → 永远 Stand**。翻译层只解决了"标签对得上"，
  还得让 LLM **真的产出** emoji。
- **修法**：
  - 场景包 `pepper_cn_v1/persona.yaml` 新增 `expression` 段
    （`emoji_map` 6 组 + `fallback_emoji` + `max_per_turn: 1` 适老化克制）；
  - `overlay/suiyue_scene.py` 渲染该段为 prompt 里的「【情绪表达】」条目，
    要求 LLM 每轮**以一个情绪 emoji 开头**（因为 server 只扫第一个字符）。
- **守护**：`overlay/test_suiyue_scene.py` 2 个新用例——渲染必须包含全部映射；
  **注入的 emoji 必须是云端 `EMOJI_MAP` 认的**（否则被静默忽略），直接复用
  `pepper/test_emotion_contract.py` 里的权威副本做跨模块校验。
- **踩坑**：写 YAML 时 `happy:🙂` 漏了空格 → `ScannerError` →
  **loader 静默降级到 `elder_cn_v1`**（只WARNING 不抛），导致 4 个测试用例
  莫名失败、`scene_pack` 变成 elder。教训：**场景包解析失败会静默降级，
  改完 YAML 务必跑 `tools/lint_yaml.py`**，否则降级会掩盖真实错误。

## 3. 产品化类（本学期后段，需 server 落地后）

### 3.1 记忆与画像（ADR-008）🟡 **2026-10-06 已决策：按 ADR-008 上数据库**
- **设计已就绪**：`docs/adr/ADR-008-记忆与画像.md`（三层记忆 + 画像三档+ 防幻觉纪律）。
- **未落地**：`profile.get` / `profile.confirm` 工具（现在隔离在 `tools_pending`，不下发给 LLM）。
- **✅ 决策（用户 2026-10-06）**：**按 ADR-008 实现**（Redis + 向量库 + MySQL），
  不采用 ADR-011 的纯文件缓存。
- **⚠️ 由此产生的 ADR-011 修订需求**（必须同步，否则两份 ADR 打架）：
  | ADR-011 原表述 | 修订后 |
  |---|---|
  | 部署形态 server-only：文件配置、**无数据库**、2–4GB RAM | **对话引擎无数据库**；<br>**记忆子系统独立部署数据库**（Redis + MySQL），不计入对话引擎进程 |
  | 记忆选`mem_local_short` | 改为 ADR-008 三层栈 |
  | 内存预算 2–4GB | 仍为对话引擎自身；**数据库另计**（Redis ~0.5GB / MySQL ~1GB 起步） |
- **理由记录**：教学演示需要**可见的三层结构**（文件缓存讲不清"三层"），
  且多租户（每学生组独立画像）是课程设计的一部分，文件缓存实现不了。
- **落地代价（诚实评估）**：偏离server-only 基线，**违背 ADR-011 决策5
  "4090 是单点故障"的降级设计**（数据库挂了三层记忆全失效）。
  建议：数据库与对话引擎**分容器**，且保留"DB 挂了→降级到本地文件缓存"的兜底路径。
- **前置**：修订 ADR-011 → 再写工具 → 再把工具移回场景包 `tools`（precheck 会自动校验）。
